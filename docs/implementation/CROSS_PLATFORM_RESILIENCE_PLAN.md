# WebGate — Cross-Platform Resilience Implementation Plan

Baseline: **2026-08-29**

This plan complements `MASTER_PLAN.md` and operationalizes `ADR-0002-CROSS-PLATFORM-RUNTIME.md`.

## CP-0 — Freeze portable contracts

Before platform-specific production code, define and test:

- `ProtectedBrowser` contract;
- `TransportProvider` contract;
- `TransportRuntime` contract (`Sidecar`, `InProcess`, `PlatformVpnService`);
- `DeviceSigner` contract with ES256 and optional Ed25519 profiles;
- `SecretStore` contract;
- `PlatformLifecycle` events;
- `DeepLink` canonical parser;
- shared `ReadinessState` / failure-reason model;
- signed policy/config wire schemas;
- OS-independent audit event IDs.

Exit: all interfaces have mock implementations and platform-free tests.

## CP-1 — Windows reference slice

Implement only enough Windows integration to prove the shared model:

```text
link -> parser -> Servo -> fail-closed proxy -> mock/real transport -> protected fixture
```

Use:

- Servo pinned LTS;
- native Rust shell;
- Windows secret/device adapter;
- local proxy that never changes its browser endpoint;
- synthetic offline page generated by the application, not remote content.

Exit:

- direct-fallback negative tests pass;
- transport restart does not require Servo reconfiguration;
- process restart revalidates policy/session.

## CP-2 — Android vertical slice

Start immediately after CP-1 browser/proxy invariant is proven.

### Packaging

- minimal Android application shell;
- arm64 first;
- Servo AAR pinned to qualified release;
- WebGate Rust shared-core JNI library;
- Outline MobileProxy AAR or equivalent mobile transport library.

### UX

```text
Telegram HTTPS App Link
 -> verified Android App Link
 -> Activity
 -> shared parser
 -> Servo
 -> protected document
```

### Security

- Android Network Security Config: cleartext denied;
- Android Keystore device key;
- ES256 challenge-response;
- no page-accessible generic JNI bridge;
- no credentials in Intents/App Links;
- app-local proxy normal mode.

### Lifecycle tests

- back/home/recents;
- rotation/config changes if supported;
- screen off/on;
- process kill;
- low-memory kill;
- app data clear;
- APK upgrade;
- Wi-Fi/mobile transition;
- airplane mode;
- Doze/battery saver;
- external VPN present.

Exit: same security invariants as Windows pass on at least two physical arm64 Android devices from different vendors.

## CP-3 — Transport runtime portability

Refactor any Windows-only transport code.

Target mapping:

| Platform | Preferred runtime | Fallback runtime |
|---|---|---|
| Windows | sidecar or in-process | alternate sidecar |
| Android | generated mobile AAR/in-process | per-app VpnService |
| Linux | sidecar/in-process | alternate sidecar |
| macOS | in-process/framework preferred | sidecar where policy allows |

A provider's protocol configuration must not encode its runtime model.

Exit: provider selection tests run against fake Sidecar and InProcess runtimes with identical browser-facing behavior.

## CP-4 — Hardware-backed device identity

Wire schema:

```text
algorithm = ES256 | ED25519
security_level = UNKNOWN | SOFTWARE | TPM | TEE | STRONGBOX | SECURE_ENCLAVE
public_key
key_id/device_id
```

Implement:

- Windows CNG/TPM adapter;
- Android Keystore adapter;
- macOS Secure Enclave/Keychain adapter;
- Linux provider abstraction.

Do not make hardware availability a universal login requirement. Server policy decides acceptable levels per tenant/use case.

Exit: challenge vectors verify across Rust and Go server implementations.

## CP-5 — Linux

Certify initially:

- Ubuntu LTS / Debian-family x86_64;
- one mainstream aarch64 Linux environment where practical.

Tasks:

- Servo package/runtime dependencies;
- secret-service integration;
- URI handler;
- sidecar supervision;
- installer/package strategy;
- Wayland/X11 validation;
- suspend/resume/network-change tests.

Avoid claiming generic "Linux support" until packaging dependencies are enumerated.

## CP-6 — macOS

Tasks:

- Servo arm64 and x86_64 qualification;
- Keychain/Secure Enclave device key;
- hardened runtime;
- code signing;
- notarization;
- URL/deep-link handling;
- native application lifecycle;
- sidecar entitlements if any;
- Apple Silicon first, Intel second.

Exit: clean machine install, Gatekeeper acceptance and upgrade path tested.

## CP-7 — Platform-independent chaos suite

Create scenario runner with cases such as:

```text
NETWORK_OFFLINE
DNS_FAILURE
PROXY_CRASH
PRIMARY_PROVIDER_CRASH
RELAY_A_DOWN
RELAY_B_DOWN
ORIGIN_DOWN
POLICY_EXPIRED
POLICY_TAMPERED
SESSION_REVOKED
DEVICE_REVOKED
CLOCK_SKEW_FORWARD
CLOCK_SKEW_BACKWARD
BROWSER_CRASH
APP_RESTART
```

Every scenario declares expected:

- browser state;
- network state;
- authorization state;
- user-visible state;
- retry policy;
- audit events.

Run the same semantic scenarios on Windows and Android Tier 1 CI/device farms.

## CP-8 — Servo qualification lane

Maintain three Servo tracks:

```text
prod      pinned LTS patch
candidate next qualified LTS/stable
research  newest stable/nightly
```

Automate:

- build smoke all platforms;
- selected WPT;
- site fixture tests;
- screenshot diffs;
- navigation-policy tests;
- proxy-failure negative tests;
- memory/CPU regression thresholds.

No dependency bot may auto-merge Servo major/monthly bumps into production.

## CP-9 — Release matrix

A release candidate cannot be called cross-platform until this matrix is green:

```text
Windows x86_64       required
Android arm64        required
Linux x86_64         required for Tier 2 release
macOS arm64          required for Tier 2 release
```

Each artifact must carry:

- application version;
- build commit;
- Servo version/commit;
- transport component versions/hashes;
- policy schema version;
- SBOM;
- signature/provenance metadata.

## CP-10 — Definition of resilient cross-platform release

A platform is supported only when:

1. installation/update is reproducible;
2. device identity persists through normal upgrades;
3. app-data deletion correctly destroys local trust and requires enrollment;
4. protected traffic cannot escape the local proxy/transport;
5. server revocation works without client update;
6. network transitions recover automatically;
7. unsupported transport conditions fail over or fail closed;
8. browser crash cannot create a direct path;
9. stale/invalid policy cannot weaken restrictions;
10. diagnostics identify the failing layer without exposing secrets.
